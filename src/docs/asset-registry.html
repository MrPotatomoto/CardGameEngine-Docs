Asset Registry

A ScriptableObject registry that maps named identifiers back to their ScriptableObject assets at runtime — required for serialization restore and undo support.

Overview

When a game snapshot is serialized, references to ScriptableObject assets (card templates, stat definitions, zone definitions, etc.) are stored as plain string identifiers. On restore, the engine needs to look up the live asset for each identifier — that lookup is the job of an IGameAssetResolver.

GameAssetRegistry is the built-in implementation. It holds serialized arrays of every asset type and builds lazy dictionaries on first access for O(1) lookups. The editor tool GameAssetRegistryGenerator auto-populates those arrays from the project in one click.

Creating a registry

  1. In the Project window, right-click → Create → Card Game Engine → Game Asset Registry.
  2. Name the asset (e.g. MyGameRegistry) and save it in your project.
  3. Select it and run Card Game Engine → Generate Asset Registry from the menu bar.

The generator scans the entire project, finds all assets of each registered type, and writes them into the registry's arrays. A summary dialog confirms the counts after completion.

Re-run after changes. Any time you add, rename, or delete a CardTemplate, StatDefinition, ZoneDefinition, or other registered asset, select the registry and run the generator again to keep it up to date.

The generator tool

Located at Card Game Engine → Generate Asset Registry. The menu item is greyed out when no GameAssetRegistry is selected in the Project window.

The tool:

  1. Scans the whole project with AssetDatabase.FindAssets for each of the seven registered types.
  2. Sorts results deterministically by their key property (e.g. TemplateId for CardTemplate) so the array order is stable across regenerations.
  3. Writes all arrays into the selected registry via SerializedObject.
  4. Calls registry.InvalidateCaches(), marks the asset dirty, and saves.

All resolve methods return null (never throw) when an asset cannot be found. A descriptive warning is logged so you can diagnose missing assets without a crash.

Wiring up for undo and serialization

Pass the registry to GameSerializer.Restore or return it from GameBootstrapper.GetAssetResolver():

C# — Custom bootstrapper with undo + registry 
public class MyBootstrapper : GameBootstrapper
{
    [SerializeField] private GameAssetRegistry _registry;

    // Supply the registry — enables UndoLastAction()
    protected override IGameAssetResolver GetAssetResolver() => _registry;

    // Use UndoableGameStateMachine to enable checkpointing
    protected override GameStateMachine CreateStateMachine(
        TurnStructureDefinition ts,
        IReadOnlyList<Player> players,
        GameContext ctx)
    {
        return new UndoableGameStateMachine(ts, players, ctx,
                                            ctx.CheckpointManager);
    }

    // Wire a keyboard shortcut to undo
    private void Update()
    {
        if (Input.GetKeyDown(KeyCode.Z) && Input.GetKey(KeyCode.LeftControl))
            UndoLastAction();
    }
}

Direct serialization restore — for loading a saved game from JSON:

C# — Loading a saved game snapshot 
string json     = File.ReadAllText(savePath);
var snapshot   = GameSerializer.Capture(context);  // or deserialize from json
var restored   = GameSerializer.Restore(snapshot, registry);

Duplicate key handling

If two assets of the same type share the same key (e.g. two CardTemplate assets both have TemplateId = "Fireball"), the registry logs a warning at cache-build time and keeps the first asset found in the sorted array. The second asset is unreachable via the resolver.

Fix duplicate keys by giving each asset a unique identifier in its Inspector fields. Key properties like TemplateId, StatName, and ZoneName are set on the asset itself, not derived from the file name.

Cache lifecycle

Dictionaries are built lazily on the first resolve call and cleared on:

  • Domain reload — OnEnable() is called after every domain reload (Editor play-mode enter, script recompile) which calls InvalidateCaches() automatically.
  • Manual call — call registry.InvalidateCaches() any time you modify the serialized arrays at runtime (uncommon outside of tests).
  • Generator run — the generator always calls InvalidateCaches() after repopulating the arrays.

Manual population

The generator is the recommended approach, but you can also populate the registry manually: select the asset in the Inspector and drag assets into the appropriate array slots. This is useful when you want to limit the resolver scope to a specific subset of project assets (e.g. only the cards in one game mode).

Tip: You can maintain multiple registry assets — one per game mode or expansion set — and swap which one is passed to GetAssetResolver() depending on which variant is being loaded.
