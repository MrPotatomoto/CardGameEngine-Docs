Stack & Priority

Full APNAP priority, stack resolution with deferred cost payment, trigger draining, and state-based action loops — all driven by GameStateMachine.

Overview

The stack is a LIFO (last-in, first-out) zone that holds spells and abilities waiting to resolve. The engine implements the Active-Player, Non-Active-Player (APNAP) priority algorithm: the active player always receives priority first, then each other player in turn order. When every player passes priority consecutively the top entry resolves, and the round restarts from the active player.

The system is split across four collaborating types:

  • StackZone — the LIFO container.
  • StackEntry — one spell or ability on the stack.
  • PendingAction — the staging area while the player is still selecting targets and paying costs.
  • GameStateMachine — runs the APNAP loop, resolves entries, drains triggers, and runs SBAs.

StackZone

The stack zone is created by ZoneManager when a ZoneDefinition with IsStack = true is registered. Access it from any system via context.ZoneManager.StackZone.

An immutable record of a spell or ability waiting to resolve. StackEntry implements ITargetable, so counter-spells and copy effects can target it directly via the targeting system.

Cost Payment Timing

Every stack entry carries a CostPaymentTiming that controls when resource costs are deducted:

ValueBehaviour
OnDeclaration Costs are paid in full when the entry is pushed. If the spell is later countered, costs are not refunded (matches Magic: The Gathering rules). This is the default.
OnResolution Resources are reserved at push time (preventing double-spending) but only deducted when the entry resolves. If the entry fizzles, reservations are released — the player is not charged.
Setting the timing: CostPaymentTiming is declared on the CardFaceDefinition in the Inspector and read by PlayCardSystem when it creates the PendingAction.

PendingAction

Before a spell or ability lands on the stack the player goes through a staging phase — selecting modes, choosing targets, paying costs. PendingAction holds all of this in-progress state and is discarded once committed or cancelled.

Stages

StageDescription
SelectingModesPlayer is choosing modal options (e.g. "deal 2 damage OR draw 2").
SelectingTargetsPlayer is picking targets. Use action.Targets.Add() and Remove().
SelectingCostsPlayer is choosing optional cost components (e.g. how many creatures to sacrifice).
AwaitingConfirmationAll selections done — waiting for the final OK.
ConfirmedSet automatically by TryCommit() on success.

TryCommit

TryCommit(context) is the key method — it validates targets, pays or reserves costs, instantiates the IEffect, and returns a ready StackEntry. Returns null on failure without side effects.

C# — Casting a spell from hand 
// 1. Ask PlayCardSystem to build the PendingAction.
var action = context.PlayCardSystem.CreatePlayCardAction(card, activePlayer);
if (action == null) return true; // can't play — pass

// 2. Let the player pick targets (your UI drives this).
action.Stage = PendingActionStage.SelectingTargets;
action.Targets.Add(chosenTarget);

// 3. Commit — pays costs, pushes to stack.
var entry = action.TryCommit(context);
if (entry == null)
{
    action.Cancel(context);
    return true; // commit failed — pass
}

// 4. Push to the stack and fire the event.
context.ZoneManager.StackZone.Push(entry);
context.EventBus.Publish(new StackEntryPushedEvent(entry.Effect.Source, entry), context);
return false; // returning false signals an action was taken
Shortcut via PlayCardSystem: context.PlayCardSystem.CommitAndPush(action) performs steps 3–4 atomically and also fires CardCastEvent. Prefer it over manual Push + Publish.

Priority Algorithm

The engine runs the APNAP loop automatically inside each priority window. You only need to provide the OnPriorityWindow callback (or its async equivalent):

C# — Wiring up the priority callback 
StateMachine.OnPriorityWindow = (player, turnCtx, gameCtx) =>
{
    // Return true  = player passes priority.
    // Return false = player took an action (pushed something to the stack).
    if (!IsHumanPlayer(player))
        return true; // AI always passes in this example

    // Present UI. If the player casts a spell here, push the entry
    // to the stack and return false.
    return _inputQueue.Count == 0; // pass if no queued actions
};

Async variant

For Unity coroutine / async/await games, set OnPriorityWindowAsync instead and drive the machine with RunGameAsync(cancellationToken). The engine will await each priority grant, letting Unity render frames between decisions.

C# — Async priority window 
StateMachine.OnPriorityWindowAsync = async (player, turnCtx, gameCtx) =>
{
    // Await real UI input from the player.
    var action = await _uiController.WaitForPlayerActionAsync(player);
    if (action == null) return true; // player pressed Pass

    // Execute the player's choice and return false (action taken).
    PushToStack(action, gameCtx);
    return false;
};

// Start the async loop (from a MonoBehaviour):
StartCoroutine(StateMachine.RunGameAsync(destroyCancellationToken).AsCoroutine());

APNAP detail

  1. SBAs are checked and all pending triggers are pushed to the stack.
  2. The active player receives priority first (PriorityGrantedEvent).
  3. If the player passes, priority moves to the next player in turn order (PriorityPassedEvent).
  4. If the player acts (returns false), SBAs + triggers are run again and the round restarts from the active player.
  5. When all players pass consecutively:
    • Stack not empty — resolve the top entry, run SBAs/triggers, restart from the active player.
    • Stack empty — the priority window closes; the phase or step ends.

Resolution Flow

When GameStateMachine resolves the top of the stack it follows this sequence:

  1. Pop the entry.
  2. If CostPaymentTiming == OnResolution and the cost hasn't been paid:
    • Call Effect.CanExecute(). If false, release all reservations and fire StackEntryFizzledEvent.
    • Otherwise, commit all ReservationTokens, then execute the effect.
  3. If CostPaymentTiming == OnDeclaration:
    • Call Effect.CanExecute(). If false, fire StackEntryFizzledEvent.
    • Otherwise, execute the effect.
  4. Fire StackEntryResolvedEvent (or StackEntryFizzledEvent).
Fizzle: An entry fizzles when all its targets have become invalid before resolution (e.g., the targeted card left the battlefield). The effect does not execute, and OnResolution reservations are released.

Auto-Actions

Some effects run automatically at the start of a phase or step — resource resets, card draws, damage dealing — without going through the stack. They are configured as EffectDefinition lists on PhaseDefinition and StepDefinition assets and executed by the engine before the first priority window. Players cannot respond to auto-actions individually.
